# ADR 0001 — Bundler parity: webpack in dev, Turbopack on Vercel

**Status:** accepted

## Context

Next.js 16 ships Turbopack as the default bundler for both `next dev` and
`next build`. On this project Turbopack's dev server exceeded our RAM budget, so
development is pinned to webpack:

```jsonc
{
  "scripts": {
    "dev": "next dev --webpack -p 8600",   // RAM: Turbopack dev is too heavy here
    "build": "next build",                  // Turbopack, as Vercel runs it
    "build:webpack": "next build --webpack" // parity build for CI
  }
}
```

That means dev and production use **different bundlers**, which is a classic
source of "works on my machine" bugs — especially for the two non-React payloads
this app depends on: the TTS Web Worker and the AudioWorklet.

## Decision

1. **Only use bundler-agnostic loading patterns.** The worker is created with
   `new Worker(new URL("../../workers/tts.worker.ts", import.meta.url), { type: "module" })`,
   which both webpack 5 and Turbopack compile into a separate chunk.
2. **No bundler-specific magic comments** (`webpackIgnore`, `turbopackIgnore`) in
   application code. A CI grep keeps them out.
3. **Keep plain-JS runtime assets in `public/` instead of the module graph.**
   - `public/stream-player.worklet.js` — webpack treats an unknown file extension
     reached through `new URL(...)` as a *raw asset* and serves it with the wrong
     MIME type, so the browser refuses to execute it as a module script.
   - `public/tokenizer.worker.js` — generated from the vendored SentencePiece
     bundle (see `scripts/copy-tokenizer-worker.mjs`). Loading it with a plain
     string URL keeps the SentencePiece wasm-in-JS out of the module graph.
   Both are loaded with string URLs, which behave identically under webpack and
   Turbopack.
4. **Bundle ONNX Runtime normally** (`import * as ort from "onnxruntime-web/wasm"`)
   and serve only the 12 MB `.wasm` binary from `public/ort/` via
   `ort.env.wasm.wasmPaths`.
5. **No `webpack` key in `next.config.ts`.** It would apply to dev only and be
   silently ignored by `next build`, which is exactly the kind of divergence this
   ADR exists to prevent.
6. **CI runs both builds** so a bundler-only regression fails the build.

## Consequences

- Two builds in CI (webpack parity + Turbopack), roughly 20 s extra.
- The AudioWorklet and the tokenizer worker are plain JavaScript in `public/`,
  so they are not type-checked. `src/audio/stream-player.worklet.ts` and
  `src/workers/vendor/tokenizerSandbox.js` remain the readable, typed sources.
- Escape hatch: if the Vercel Turbopack build ever mis-bundles the worker, set
  the project's build command to `next build --webpack`.

## Addendum — HTTPS in development

`pnpm dev` serves **https** on port 8600 using a self-signed certificate
generated by mkcert (`scripts/dev-certs.mjs`).

This is not a preference. `crossOriginIsolated` — the gate for
`SharedArrayBuffer`, and therefore for multi-threaded ONNX Runtime wasm — is only
granted to a *secure context*. `http://localhost` counts as one, but any other
host does not: the moment you open the dev server from a phone or a second
machine on the LAN, the document would stop being cross-origin isolated and the
engine would quietly run single-threaded.

- `mkcert/` holds the project-local CA, the leaf certificate and the key, and is
  git-ignored. `CAROOT` points at it, so nothing leaks into `~/.mkcert`.
- The certificate covers `localhost`, `127.0.0.1`, `::1` and every detected LAN
  address; `node scripts/dev-certs.mjs --host <name>` adds more.
- Adding the CA to the system trust store needs root on Linux. When that is not
  possible the script says so and still produces working certificates — the
  browser just shows a warning.
- `pnpm dev:http` keeps a plain-HTTP escape hatch for localhost-only work.
- `scripts/e2e.mjs` launches Chromium with `--ignore-certificate-errors`.
